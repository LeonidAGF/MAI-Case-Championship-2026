# Атлас доступности территорий СКФО — бэкенд

Бэкенд кейса А2. Это один сервис на FastAPI. Он считает индекс доступности территорий,
объясняет оценку, сравнивает территории, прогоняет сценарии «что если» (W1–W10) и отвечает
в чате. Вместе с ним в Docker запускаются база данных, Redis и мониторинг.

ML-часть бэкенд не меняет. Файлы ML в `../data`, `../graph`, `../clast` и `../scripts` он только
читает, а модель индекса подключается через контракт (см. [Данные и интеграция с ML](#данные-и-интеграция-с-ml)).

### 1. Бэкенд

Команды одинаково работают в PowerShell и bash. Здесь и дальше команды `docker compose` и
`python` выполняются из папки `backend`.

Если файл `backend/.env` уже есть, не копируйте его заново: в нём могут быть ваши порты и ключ
Anthropic API. Перенесите из `.env.example` только недостающие переменные.

```bash
cd backend
cp .env.example .env              # настройки и порты
docker compose up -d --build      # база, Redis, API и мониторинг
docker compose run --rm api python -m app.cli seed   # справочники, территории, реальные данные OSM, база знаний чата
```

Что делают эти команды:

- `up` собирает образы и запускает PostgreSQL 16 (с PostGIS и pgvector), Redis, API и
  мониторинг (Prometheus, Grafana, Loki, Alloy). При старте API сам применяет миграции базы.
- `seed` загружает справочники, 7 субъектов, 144 района и 3403 населённых пункта (НП), объекты
  и признаки из OpenStreetMap (`geo-embeddings/data`, см. [Данные](#данные)) и базу знаний чата.
  Синтетические значения от старых версий удаляются. Команду можно запускать повторно,
  дубликатов не будет.

### 2. Фронтенд

Во втором терминале, из корня репозитория:

```bash
cd web
npm install    # зависимости, достаточно один раз
npm run dev    # приложение на http://localhost:3000
```

Фронтенд обращается к API по адресу `http://localhost:8000`. Если API работает на другом адресе,
укажите его в `web/.env.local`, например `NEXT_PUBLIC_API_URL=http://localhost:8080`. Бэкенд
принимает запросы браузера только с адресов из `CORS_ORIGINS` (по умолчанию `http://localhost:3000`).

### 3. Проверка

| Что                        | Адрес                         | Примечание                                             |
|----------------------------|-------------------------------|--------------------------------------------------------|
| Веб-приложение             | http://localhost:3000         | после `npm run dev`                                    |
| Документация API (Swagger) | http://localhost:8000/docs    | контракт также лежит в `openapi.json`                  |
| Состояние API              | http://localhost:8000/healthz | поле `feature_data` показывает, какие данные загружены |
| Grafana                    | http://localhost:3001         | логин `admin`, пароль из `GRAFANA_ADMIN_PASSWORD`      |
| Prometheus                 | http://localhost:9090         |                                                        |
| Loki                       | http://localhost:3100/ready   | должен ответить `ready`                                |

Порты меняются в `backend/.env`: `API_PORT`, `DB_PORT`, `REDIS_PORT`, `GRAFANA_PORT`,
`PROMETHEUS_PORT`, `LOKI_PORT`. Grafana работает на 3001, потому что порт 3000 занимает фронтенд.
Grafana, Prometheus и Loki слушают только `127.0.0.1`: мониторинг рассчитан на локальный показ.

### Включить чат

Добавьте ключ Anthropic API в `backend/.env` (`ANTHROPIC_API_KEY=...`) и пересоздайте контейнер
API командой `docker compose up -d api`. Команда `docker compose restart` новые переменные из
`.env` не подхватывает. Подробнее — в разделе [Чат-ассистент](#чат-ассистент). Остальной API
работает и без ключа.

### Без Docker (только API)

Нужны Python 3.12+ и запущенные база и Redis, например `docker compose up -d db redis`.

```bash
python -m venv .venv
.venv\Scripts\Activate.ps1      # Windows PowerShell; в Linux и macOS: source .venv/bin/activate
pip install -e ".[dev]"         # для векторного поиска в чате: pip install -e ".[dev,embeddings]"
python -m app.cli migrate
python -m app.cli seed
uvicorn app.main:app --reload
```

В Linux, macOS и WSL есть короткие команды из `Makefile`: `make up`, `make seed`,
`make seed-osm`, `make logs`, `make test`, `make openapi`.

## Данные

Все значения признаков реальные. OpenStreetMap читается один раз скриптами ML, результаты лежат в
репозитории в виде CSV в `geo-embeddings/data` (в контейнере — `/osm`, настройка `OSM_DATA_DIR`).
Бэкенд только загружает их командой `seed` или `seed-osm` и во время работы к OSM не обращается.

- `osm_poi.csv` — 15 372 объекта (больницы, поликлиники и ФАП, школы, детские сады, колледжи и
  вузы, кафе, ДК, спорт, парки, ТЦ, рынки, ЖД- и автостанции, аэропорты) → таблица `poi`. Слой
  нужен и сценарию W2 «закрытие больницы».
- `osm_features.csv` — признаки F01–F17 и F21 для 3403 НП: время на машине по дорожному графу ML,
  число объектов в пределах 15 и 30 минут → `feature_value` с источником `osm+ml-graph`.

Данные OSM на 11.11.2026, © участники OpenStreetMap, лицензия ODbL. Как пересчитать — в
`scripts/AGENT.md` (шаги 20 и 21).

Чего пока нет: статистики Росстата, ЕМИСС и ФНС (F18–F20, F22–F30) и климата (F24–F26). Эти
признаки не участвуют в расчёте: их вес внутри субиндекса делится между признаками с данными, а
субиндекс «Климат» и бейдж привлекательности пустые. В объяснениях такие признаки помечены
«нет данных — признак не участвует в расчёте». Время пешком не считается: для профилей без машины
берётся время на машине. Статистику загружайте командами `load-stats` и `load-features`.

Синтетические значения (`source='synthetic-demo'`, дата `1900-01-01`) остались только в
тестовой базе (`tests/synthetic.py`). Если они найдутся в рабочей базе после старых версий, это
видно везде: `/healthz` пишет `feature_data: synthetic-demo (NOT real data)`, чат предупреждает,
в Grafana индикатор «Синтетические данные» показывает 1, а в Prometheus срабатывает правило
`AtlasSyntheticDataPresent`. Команды `seed` и `clear-demo-features` их удаляют.

```
app/
  main.py          приложение: CORS, сжатие GZip, заголовок X-Process-Time, обработка ошибок
  container.py     общие сервисы процесса (движок индекса, кеши, OSRM, чат) и их прогрев
  core/            настройки из .env, единый формат ошибок, лимиты запросов, журналы, метрики
  db/              модели таблиц (ORM) и сессии базы
  api/
    routes/        эндпоинты; api/schemas.py — типизированный контракт для фронтенда
  profiles/        профили пользователей (раздел 9.2 отчёта), кодирование параметра p, пресеты
  modelcfg.py      загрузка и проверка YAML модели — контракт с ML
  scoring/         расчёт индекса:
    contract.py    интерфейс движка для ML
    reference.py   встроенный движок по формуле 4.3
    matrix.py      матрица признаков (наследование от района и субъекта, авто или пешком)
    service.py     кеши и поправки сценариев what-if
    snapshots.py   снимки результатов (index_result + component)
  explain/         «водопад» относительно типичной территории кластера и тексты причин
  compare/         сравнение 2–3 территорий одного кластера
  whatif/          каталог W1–W10, движок сценариев, клиент OSRM
  chat/            клиент Claude (llm.py), 3 инструмента, RAG, проверка чисел, 10 контрольных вопросов
  etl/             загрузчики: территории, признаки, POI, матрица времени, статистика, «Точно»,
                   база знаний, отчёт о полноте
  cli.py           служебные команды: python -m app.cli --help
migrations/        миграции Alembic; написаны вручную, тесты сверяют их с моделями
config/
  model.default.yaml   резервная копия модели из таблиц 2–5 отчёта (основная — у ML)
seeds/              субъекты, привязка 144 районов к субъектам, ручные правки кластеров,
                    официальные счётчики POI
observability/      настройки мониторинга: Prometheus, Grafana, Loki, Alloy
docker/db/          образ PostgreSQL с PostGIS и pgvector, создание тестовой базы
tests/              unit- и интеграционные тесты
```

Таблицы из раздела 7 отчёта: `territory`, `cluster`, `feature`, `feature_value`, `profile`,
`index_result`, `component`, `scenario`, `scenario_run`, `knowledge_chunk`. Служебные таблицы:

- `subindex` — субиндексы;
- `model_version` — какая версия модели загружена;
- `etl_run` — ревизии данных и отчёты загрузок;
- `poi` и `travel_time` — объекты и время до них для сценариев W1–W5 и W9.

## API

Полный контракт — в Swagger (`/docs`) и в `openapi.json`, который обновляет команда
`python -m app.cli export-openapi`. Ниже все 10 эндпоинтов из таблицы 10 отчёта и вспомогательные.

| Назначение          | Эндпоинты                                                                                                                                                                                                                           |
|---------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Территории и карта  | `GET /territories` — список с фильтрами `level`, `cluster`, `region`, `parent_id`, `q`, `bbox` и пагинацией; `GET /territories/geojson` — слои карты (`with_index` добавляет индекс); `GET /territories/{id}` — карточка территории |
| Индекс              | `GET /index?territory_id=…` или `?cluster=…`; параметры `sort`, `region`, `scenario_run_id` и `group_by=municipality\|region` для заливки карты по районам или субъектам                                                            |
| Объяснение          | `GET /explain/{id}` — водопад вкладов, три главных плюса и минуса                                                                                                                                                                   |
| Сравнение           | `POST /compare` — 2–3 территории одного кластера                                                                                                                                                                                    |
| Сценарии            | `GET /whatif/scenarios` — каталог для формы; `POST /whatif/run` — прогон; `GET /whatif/runs/{id}` — повторно открыть прогон                                                                                                         |
| Профили             | `GET /profiles/presets`, `POST /profiles/encode`, `GET /profiles/decode`                                                                                                                                                            |
| Справочники         | `GET /features`, `GET /clusters`, `GET /regions`                                                                                                                                                                                    |
| Данные              | `GET /data/coverage` — отчёт о полноте данных                                                                                                                                                                                       |
| Чат и база знаний   | `POST /chat` (поток SSE); `GET /knowledge/status`, `GET /knowledge/search`, `GET /knowledge/chunks/{id}`                                                                                                                            |
| Служебные           | `GET /healthz` — состояние; `GET /metrics` — метрики для Prometheus                                                                                                                                                                 |

Общие правила API:

- **Профиль** передаётся как `profile=<id пресета>` или как `p=<закодированный профиль>`; в
  POST-запросах `p` можно передать строкой или объектом. `p` — это base64url от JSON или от JSON,
  сжатого deflate-raw (в браузере — `new CompressionStream('deflate-raw')`). Пример из отчёта
  `?p=eyJ2IjoxLCJwcm9maWxlIjoicGVuc2lvbmVyIn0` тоже работает. Недостающие поля профиля берутся
  из пресета. Неизвестная версия профиля даёт `422 profile_version_unsupported`, и фронтенд
  сбрасывает профиль на пресет.
- **Ошибки** всегда приходят в одном формате: `{"code", "message", "details?"}`. Основные коды:
  `validation_error`, `not_found`, `territory_not_scored`, `cluster_mismatch`, `profile_*`,
  `scenario_*`, `poi_not_found`, `rate_limited` (с заголовком `Retry-After`), `chat_disabled`.
- **Водопад** (`/explain`) начинается с `baseline` — «типичной территории кластера», то есть
  суммы медианных вкладов. Каждый шаг `delta` показывает, насколько признак территории отличается
  от типичного, и `baseline + сумма delta = total` (округление сумму сохраняет). Плюсы и минусы —
  три самых больших `delta` в каждую сторону; в текстах нет кодов признаков.
- **Снимки** результатов (`index_result` + `component`) не меняются и не дублируются: один
  снимок на сочетание территории, профиля, сценария, версии модели и ревизии данных.
  Пользовательские профили в базе не хранятся, только хеш их расчётной части.
- **Лимиты.** Число запросов ограничено по IP через Redis (настройки `RATE_LIMIT_*` в `.env`).
  Кроме того, `p` — до 2000 символов, сравнение — 2–3 территории, страница — до `max_page_size`
  записей, чат — до 30 сообщений по 4000 символов.

## Сценарии what-if

Сценарий — это набор поправок к значениям признаков (`feature_value`). Поправки сохраняются в
`scenario_run.overrides`, а индекс затем считается обычным способом. Нормировка остаётся
подогнанной по базовым данным, поэтому территории, которых сценарий не касается, не меняются.

| Код | Что моделирует                       | Где задаётся        | Что меняется                                                                                               |
|-----|--------------------------------------|---------------------|------------------------------------------------------------------------------------------------------------|
| W1  | Открытие больницы или ФАП            | точка на карте      | время до нового объекта                                                                                    |
| W2  | Закрытие больницы (ремонт, карантин) | точка или `poi_id`  | время до следующего ближайшего объекта                                                                     |
| W3  | Открытие детского сада или школы     | точка на карте      | время до нового объекта                                                                                    |
| W4  | Открытие колледжа или филиала вуза   | точка на карте      | время до нового объекта                                                                                    |
| W5  | Открытие ЖД-платформы или станции    | точка на карте      | время до нового объекта                                                                                    |
| W6  | Ремонт трассы                        | район или список НП | время до регионального центра сокращается на `percent` %                                                   |
| W7  | Автобусный маршрут «село → райцентр» | район или список НП | доля жителей без регулярного сообщения (F19) становится 0, время до остановки (F17) — `stop_access_min`    |
| W8  | Расширение аэропорта, новые рейсы    | точка или `poi_id`  | время до аэропорта в радиусе сокращается на `percent` %                                                    |
| W9  | Открытие ТЦ, кинотеатра или парка    | точка на карте      | время до нового объекта                                                                                    |
| W10 | Пакет для района: W1 + W3 + W7       | район               | без `steps` автоплан ставит ФАП и школу в сёла с худшей доступностью и пускает автобус для всех сёл района |

**Как считается время до нового объекта** (W1, W3, W4, W5, W9). Если подключён OSRM
(`OSRM_CAR_URL`, `OSRM_FOOT_URL`), время берётся из его таблицы маршрутов. Иначе оно
оценивается аналитически: расстояние по прямой умножается на 1,3 (поправка на извилистость дорог)
и делится на скорость — 50 км/ч на машине или 4,5 км/ч пешком, но не меньше 3 минут. В этом случае
ответ содержит предупреждение.

**Как считается закрытие больницы** (W2):

1. Если загружена матрица `travel_time`, берётся время до следующего ближайшего объекта по ней.
2. Если матрицы нет, время пересчитывается по отношению расстояний до следующего объекта из слоя `poi`.
3. Если слоя POI рядом нет (`load-poi` не запускали), закрываемый объект считается стоящим в
   указанной точке. НП считается зависевшим от него, если точка не дальше его текущего
   ближайшего объекта (с запасом: × 1,25 + 2 минуты). Новое время — самый короткий путь через
   соседний НП, который обслуживает другой объект: время до соседа плюс значение признака у
   соседа. Ответ содержит предупреждение, что это оценка.

Ответ сценария содержит значения до и после, изменения субиндексов, победителей и проигравших
и текстовое объяснение.

**Параметры** каждого сценария проверяются строго: лишнее или неверное поле даёт
`422 scenario_params_invalid`, а в `details` указаны поле и причина. Каталог `GET /whatif/scenarios`
подсказывает форме, что нужно каждому сценарию:

- `target` — `point` (точка на карте) или `municipality` (район);
- `kinds` — варианты объекта с русскими подписями;
- `example` — рабочий пример запроса. `municipality_id` в нём берётся из базы, поэтому пример
  запускается как есть.

## Чат-ассистент

Чат работает на Claude через Anthropic API (официальный SDK `anthropic`), клиент лежит в
`app/chat/llm.py`, цикл с инструментами — в `app/chat/service.py`. Модели доступны три инструмента:
`get_index`, `compare_territories` и `run_scenario`. Они принимают названия НП.

Все числа о конкретных территориях модель берёт из этих инструментов. Бэкенд проверяет ответ:
каждое число должно встречаться в результатах инструментов, неподтверждённые числа пользователю не
показываются. Итог проверки приходит в `done.grounding`. Если ключа нет или API недоступен, чат
присылает событие `error`, а остальной API продолжает работать. Ход без ответа тоже заканчивается
событием `error`, а пустые и неотвеченные сообщения из истории бэкенд отбрасывает, поэтому сбой
одного хода не ломает следующий.

Ответ приходит потоком SSE с событиями `meta`, `delta`, `tool_call`, `tool_result`, `citations`,
`error` и `done`.

### Настройка

1. Создайте ключ в консоли platform.claude.com (раздел API keys) и добавьте его в `backend/.env`:

   ```
   ANTHROPIC_API_KEY=<ключ>
   ```

   Файл `.env` в git не попадает, поэтому ключ передавайте коллегам вне репозитория.
2. Модель и глубина рассуждений: `LLM_MODEL` (по умолчанию `claude-sonnet-5-5`, быстрее и дешевле —
   `claude-haiku-5-5`) и `LLM_EFFORT` (`low`, `medium` по умолчанию, `high`). Для Sonnet 5.5
   включён серверный резерв на случай отказа модели (`LLM_FALLBACKS=true`); у Haiku его нет.
3. Примените настройки: `docker compose up -d api`.
4. Проверьте подключение. Проверка бесплатная: она только читает описание модели.

   ```bash
   docker compose run --rm api python -m app.cli chat-check    # без Docker: python -m app.cli chat-check
   ```

   Ошибка доступа (403) обычно значит, что запрос пришёл из страны, где Anthropic API недоступен.

**Кеширование.** Описания инструментов и постоянная часть системной подсказки кешируются, поэтому
второй и следующие шаги одного хода дешевле и быстрее.

**Контрольные вопросы.** `python -m app.cli chat-eval --yes` прогоняет 10 вопросов и проверяет
числа в ответах. Команда платная: она вызывает Anthropic API.

### База знаний и RAG

Кроме функций, чат опирается на базу знаний: фрагменты методики и проверенные материалы команды.
Поиск гибридный: русский полнотекстовый индекс PostgreSQL и точный косинусный поиск pgvector по
локальным мультиязычным эмбеддингам FastEmbed. В Docker модель эмбеддингов загружается при сборке
образа; без Docker установите `pip install -e ".[embeddings]"`.

Команда `seed` обновляет справочник методики из активного `MODEL_CONFIG_PATH` и индексирует его.
Повторный `seed` заменяет справочник без дубликатов. Если справочники и территории уже загружены,
достаточно выполнить:

```bash
docker compose run --rm api python -m app.cli seed-knowledge
```

Поиск проверяется без ключа LLM:

1. http://localhost:8000/knowledge/status — поля `chunks` и `embedded` должны быть больше нуля.
2. http://localhost:8000/knowledge/search?q=больница&limit=5 — в ответе найденные фрагменты,
   `retrieval_methods` (`vector` и/или `full_text`) и `source_url`.
3. `/knowledge/chunks/{id}` — полный текст фрагмента.

Параметры этих маршрутов описаны в `/docs`.

Свои материалы добавляются так:

```bash
docker compose run --rm api python -m app.cli load-knowledge /data/файл.jsonl --source team-data --replace --embed
```

Файл кладите в папку `data` в корне репозитория: в контейнере она видна как `/data`. Формат —
JSONL, один объект на строку. Обязательное поле — `text`; необязательные — `title`, `source_url`,
`external_id` или `territory` вместе с `region`. Для проверенных материалов указывайте источник и
ссылку на оригинал. Точные баллы и минуты бот всё равно берёт из функций расчёта, а не из текстов
базы знаний.

Сам чат проверяется в веб-приложении после настройки ключа; источники появляются под ответом.
Без ключа работает только поиск по базе знаний.

## Данные и интеграция с ML

### Как подключается модель ML

Бэкенд в модель не вмешивается: она подключается к нему в пяти местах.

1. **Конфиг модели** — YAML по схеме `config/model.default.yaml`: субиндексы, 30 признаков
   (направление, вес, уровень), параметры кластеров, пресеты. ML хранит свой файл и указывает
   путь в `MODEL_CONFIG_PATH`. При старте бэкенд проверяет схему и записывает версию и хеш в
   `model_version`.
2. **Калькулятор индекса** — класс с интерфейсом `app.scoring.contract.IndexEngine`
   (`name`, `version`, `score(ScoreRequest) -> {territory_id: TerritoryScore}`). Он подключается
   через `SCORING_ENGINE=пакет.модуль:Класс`.
   - Бэкенд сам собирает матрицу признаков. Статистику, которая публикуется по районам и
     субъектам (F18–F23, F27–F30), НП наследуют от них. Режим «авто» или «пешком» выбирается по
     фильтру «Мобильность».
   - Бэкенд передаёт движку профиль и параметры кластера, сохраняет снимки и строит объяснения.
   - Обязательные свойства движка проверяет `tests/unit/test_engine_contract.py`: детерминизм,
     сумма вкладов равна `total`, значения в допустимых диапазонах. Этот тест можно прогнать и
     против движка ML.
   - Пока движок ML не подключён, работает встроенный `reference.py`: формула 4.3 с winsorize и
     квантильной нормировкой 5.3. Фильтры профиля он не интерпретирует.
3. **Признаки** загружает `load-features file.parquet|csv`. Форматы:
   - длинный: `<ключ>, feature_code, raw_value[, mode, as_of, imputed]`;
   - широкий: `<ключ>, F01, F01@foot, …`.

   Ключ — одно из полей `settlement_osm_id`, `osm_id`, `municipality_osm_relation_id`,
   `region_code`, `external_id`, `territory_id`. `mode` — `car`, `foot` или `any`. История значений
   хранится по `as_of`.
4. **POI и матрица времени.** `load-poi` загружает объекты: GeoJSON из osmium или таблицу с lon/lat;
   категории определяются по тегам OSM. `load-travel-times` загружает матрицу времени
   (`<ключ>, poi_id|poi_external_id, mode, seconds|minutes`).
5. **OSRM** для точного what-if — адреса `OSRM_CAR_URL` и `OSRM_FOOT_URL` (контейнеры MLOps).
   Без них или при сбое сценарии считаются аналитически, а ответ содержит предупреждение.

### Команды загрузки

Все команды запускаются как `python -m app.cli <команда>`, в Docker — как
`docker compose run --rm api python -m app.cli <команда>`. Параметры команды показывает `--help`.

| Команда                                                                                | Что делает                                                                                                                                                       |
|----------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `seed` | `seed-reference` + `load-territories` + `seed-osm` + `seed-knowledge` |
| `seed-reference`                                                                       | справочники из YAML модели: субиндексы, кластеры, признаки, пресеты, сценарии                                                                                    |
| `load-territories [--data-dir]`                                                        | субъекты (объединение полигонов), 144 района (геометрии в PostGIS), 3403 НП рабочей выборки ML, кластеры А/Б/В                                                   |
| `load-features`, `load-poi`, `load-travel-times`                                       | признаки, объекты и матрица времени от ML (см. выше)                                                                                                             |
| `load-stats FILE --feature F23 [--indicator …] [--year …] [--learn-oktmo] [--dry-run]` | статистика ЕМИСС, Росстата БДМО (выгрузки «Точно»: CSV в UTF-8 с разделителем `;`), ФНС и «широкие» таблицы по годам → значения признака для районов и субъектов |
| `load-od-matrix FILE [--out pairs.csv] [--to-features]`                                | матрица «Точно» город — город → нормализованные пары для ML (и признаки F14/F21 для городов СКФО)                                                                |
| `load-knowledge`, `seed-knowledge`                                                     | база знаний чата (md, txt, jsonl, csv)                                                                                                                           |
| `seed-osm [--osm-dir]` | объекты и признаки OSM из `OSM_DATA_DIR` (`osm_poi.csv`, `osm_features.csv`); удаляет синтетические значения |
| `clear-demo-features` | удалить синтетические значения, оставшиеся от старых версий |
| `coverage`                                                                             | отчёт о полноте (то же, что `GET /data/coverage`): заполненность признаков по субъектам, POI, сверка с `seeds/official_poi_counts.csv`                           |
| `export-openapi`                                                                       | обновить `openapi.json`                                                                                                                                          |
| `chat-check`, `chat-eval`                                                              | проверка подключения чата и контрольные вопросы                                                                                                                  |

**Кластеры** (раздел 4.1 отчёта):

- А — население больше 50 тыс. или столица субъекта;
- Б — город, посёлок или райцентр (крупнейший НП муниципального района или округа);
- В — остальные сёла.

Причина выбора кластера записана в `territory.meta.cluster_reason`, ручные правки лежат в
`seeds/cluster_overrides.csv`.

**Статистика сопоставляется с районами** по шагам: сначала по ОКТМО, затем по субъекту,
нормализованному названию и типу (городской округ или район), затем по началу названия с защитой
от ложных совпадений. Строки поселений отбрасываются.

**Ревизии данных.** Каждая загрузка записывается в `etl_run`. Новая ревизия сама сбрасывает кеши
API, это занимает не больше 3 секунд.

## Мониторинг

Мониторинг запускается тем же `docker compose up`, что и API, и рассчитан на локальный показ.

- **Prometheus** раз в 15 секунд собирает метрики с `/metrics` API и хранит их 15 дней.
- **Loki** хранит журналы API 7 дней.
- **Alloy** читает файлы журналов API и передаёт новые строки в Loki.
- **Grafana** показывает панели по метрикам и журналам.

Настройки в `backend/.env`: `GRAFANA_ADMIN_PASSWORD`, `GRAFANA_PORT`, `PROMETHEUS_PORT`,
`LOKI_PORT` и `METRICS_REFRESH_SECONDS`.

### Панели Grafana

Откройте http://localhost:3001 и войдите с логином `admin` и паролем из `GRAFANA_ADMIN_PASSWORD`.
По умолчанию это `atlas-demo-change-me`; такой пароль годится только для локального показа. Папка
«Атлас СКФО» с панелями создаётся автоматически.

| Панель                                                                            | Что показывает                                                                                                                                                                                                       |
|-----------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| [01 · Сервис и скорость](http://localhost:3001/d/atlas-service)                   | доступность API, запросы в минуту, ошибки 5xx, p95 времени ответа по маршрутам, время расчёта индекса, работу кешей и Redis                                                                                          |
| [02 · Качество и происхождение данных](http://localhost:3001/d/atlas-data)        | работает ли сбор, есть ли синтетика, ревизию данных, полноту признаков по субъектам, возраст источников, загрузки ETL (последняя успешная, ошибки, импутированные значения), POI в сравнении с официальным счётчиком |
| [03 · Сценарии, маршрутизация и журналы](http://localhost:3001/d/atlas-scenarios) | успешные и неудачные сценарии, p95 по коду и методу, OSRM (доступность, запросы, p95), аналитические замены и их причины, затронутые территории, среднее изменение индекса, ошибки и журналы API                     |

**Почему панели пустые.** Графики частоты и p95 строятся по окну 5 минут, поэтому до первых
запросов в них ничего нет. Откройте [каталог сценариев](http://localhost:8000/whatif/scenarios) и
несколько страниц приложения, а для графиков сценариев запустите сценарий в интерфейсе what-if.

Показатели данных обновляются при старте API и затем каждые `METRICS_REFRESH_SECONDS` секунд
(по умолчанию 300). Для показа можно выставить 30 до запуска. Чтобы панели сразу увидели только
что загруженные данные, выполните `docker compose restart api`.

- [Метрики API](http://localhost:8000/metrics) — текст в формате Prometheus.
- [Цели Prometheus](http://localhost:9090/targets) — цель `atlas-api` должна быть в состоянии `UP`.
- [Готовность Loki](http://localhost:3100/ready).

### Оповещения

На странице [Alerts](http://localhost:9090/alerts) в Prometheus четыре правила. Они локальные:
уведомления никуда не рассылаются.

| Правило                     | Когда срабатывает                                                                                   |
|-----------------------------|-----------------------------------------------------------------------------------------------------|
| `AtlasApiUnavailable`       | Prometheus не получает метрики API дольше минуты                                                    |
| `AtlasHighServerErrorRate`  | больше 5% ответов с кодом 5xx в течение 5 минут, если запросов больше 0,1 в секунду                 |
| `AtlasDataMetricsStale`     | сбор метрик качества данных падает или не обновлялся дольше 900 секунд (три обычных цикла по 300 с) |
| `AtlasSyntheticDataPresent` | в базе синтетические признаки; это напоминание, а не ошибка                                         |

### Журналы

В Grafana откройте **Explore**, выберите источник **Loki** и выполните запрос:

```logql
{job="atlas",service="api"} | json
```

Только ошибки и предупреждения:

```logql
{job="atlas",service="api"} | json | level=~"error|warning"
```

Чтобы проверить, что журналы доходят до Loki, откройте `GET /whatif/scenarios` и найдите этот
запрос в Explore. Журналы самих контейнеров:

```bash
docker compose logs --tail 100 api alloy loki prometheus grafana
```

Как это устроено:

- API работает в двух процессах-воркерах (`WEB_CONCURRENCY=2`). Каждый пишет JSON-журнал в stdout
  и в свой файл.
- Alloy читает эти файлы из общего тома `api-logs` и передаёт новые строки в Loki.
- Файл журнала сменяется после 10 МБ, хранятся до трёх старых копий. При старте API удаляются
  файлы старше семи дней.
- Метрики обоих воркеров Prometheus получает вместе: Python-клиент работает в multiprocess-режиме.
  Его каталог временных файлов очищается при старте контейнера API.

### Изменение панелей

JSON-файлы в `observability/grafana/dashboards` создаёт скрипт `observability/build_dashboards.py`,
поэтому правьте скрипт, а не JSON. После изменения выполните:

```bash
python observability/build_dashboards.py
docker compose restart grafana
```

### Метрики без Docker

С одним процессом Uvicorn ничего настраивать не нужно. Для нескольких воркеров заранее задайте
`PROMETHEUS_MULTIPROC_DIR` и очищайте этот каталог перед каждым запуском.

## Тесты

```bash
pytest tests/unit -q    # без базы данных
pytest tests -q         # вместе с интеграционными, нужен TEST_DATABASE_URL
```

Для интеграционных тестов compose заранее создаёт базу `atlas_test`. Укажите её в переменной
окружения `TEST_DATABASE_URL` или строкой в `backend/.env`:

```
TEST_DATABASE_URL=postgresql+asyncpg://atlas:atlas@localhost:5432/atlas_test
```

Интеграционные тесты:

- пересоздают схему (`downgrade base → upgrade head`);
- проверяют, что миграция совпадает с моделями (`alembic check`);
- загружают реальные территории ML;
- прогоняют API, ETL и чат. Вместо Claude чат использует подставной клиент, поэтому сеть не
  нужна и токены не тратятся;
- последним модулем загружают реальные данные OSM из `geo-embeddings/data` и проверяют API на них.

## Ограничения и открытые вопросы

- В таблице 2 отчёта веса пресета «Риелтор / инвестор» в сумме дают 90, а не 100. При загрузке они
  пропорционально приводятся к 100, а в журнал пишется предупреждение. Нужно решение ML или лида.
- Райцентры определяются эвристикой: крупнейший НП района. Ошибки правятся в
  `seeds/cluster_overrides.csv`.
- У районов из данных ML нет ОКТМО. Он заполняется при загрузке статистики с `--learn-oktmo`; дамп
  ГАР ФИАС не разбирается.
- Аналитический what-if — это оценка по прямой с поправкой на извилистость дорог. Точное время
  будет только с подключённым OSRM.
- Индекс не учитывает сезонность, пробки, качество услуг и цены на жильё.
- Индекс и снимки считаются для населённых пунктов. Значения районов и субъектов — агрегаты
  (`group_by`).
