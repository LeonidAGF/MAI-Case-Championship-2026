# Рельеф SRTM для расчёта времени доезда скорой

35 плиток высот 1°×1° под дорожным графом СКФО (широта 41–47°, долгота 40–49°). Их читает только
`python -m app.cli load-ambulance`: из них берутся высота дорог и уклон вдоль направления движения.
Во время работы API к ним не обращается, в интернет за рельефом не ходит.

| | |
|---|---|
| Формат | HGT в gzip (`N43E044.hgt.gz`): 1201×1201 высот int16 в метрах, big-endian, первая строка — северный край, −32768 — пропуск |
| Разрешение | 3″ (≈90 м по широте, ≈68 м по долготе на 43° с. ш.) |
| Источник | SRTM 1″ без пропусков из открытых данных AWS «Terrain Tiles» (формат skadi): `https://elevation-tiles-prod.s3.amazonaws.com/skadi/{N43}/{N43E044}.hgt.gz` |
| Обработка | среднее 3×3 высот SRTM 1″ вокруг каждой третьей точки, как NASA получала SRTM3 из SRTM1; округление до метра |
| Загружено | 13.11.2026 |
| Размер | ≈41 МБ |

Почему 3″, а не исходные 1″ (≈300 МБ): модель всё равно сглаживает высоты окном ≈90 м против шума SRTM.
Проверка на всех 3 397 населённых пунктах с оценкой: время доезда по плиткам 3″ отличается от 1″
в среднем на 1,5 секунды (95% пунктов — не больше 8 секунд, максимум 0,7 минуты), норматив 20 минут
поменялся у 3 пунктов, высота пунктов — в среднем на 0,7 м.

## Как обновить

Недостающие плитки (например, если граф расширится) добавляет `python -m app.cli fetch-srtm`: скачивает
SRTM 1″ и сохраняет 3″. Повторный запуск на тех же данных даёт те же байты. Чтобы пересобрать плитки
из своих файлов SRTM 1″ (`.hgt`, `.hgt.gz` или `.zip`): `python -m app.cli fetch-srtm --source-dir <папка>`
(в папке `data/srtm` не должно быть плиток с теми же именами). Исходное разрешение сохраняет
`--arcsec 1`, но плитки 1″ занимают в 8 раз больше места.
