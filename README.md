# Pulse Score — атлас доступности территорий СКФО

**Pulse Score** — веб-сервис с картой Северо-Кавказского федерального округа. Для каждого из 3 403 населённых пунктов он показывает индекс доступности жизни от 0 до 100 и семь субиндексов, сравнивает территории, проверяет сценарии «что если» и отвечает на вопросы в чате.

Проект сделан для кейса А2 «Индекс транспортной связанности», MAI Case Championship 2026. Команда: Team_Epsilon.

> **Данные.** Сервис работает на реальных данных: 18 из 30 признаков (медицина, образование, досуг, транспорт, рынок труда) посчитаны по OpenStreetMap на дорожном графе ML для всех 3 403 населённых пунктов. Статистики Росстата, ФНС и климата в OSM нет, поэтому эти признаки пока не участвуют в расчёте, а субиндекс «Климат» и бейдж привлекательности пустые. Подробности: [Данные](#данные).

## Что умеет сервис

- **Карта и индекс.** Оценка 0–100 для каждого населённого пункта и сводка по районам и субъектам.
- **Семь субиндексов:** медицина, образование, досуг, транспорт, работа, климат, привлекательность. Видно, что тянет территорию вниз.
- **Личный профиль** приоритетов (семья, пенсионер, риелтор и другие). Регистрация не нужна: профиль хранится в параметре `p` адреса и в браузере.
- **Честное сравнение.** Территории сравниваются внутри кластеров похожести: А (города от 50 тыс. и столицы), Б (райцентры и малые города), В (сёла).
- **Объяснение оценки.** «Водопад» вкладов признаков относительно типичной территории кластера.
- **Сценарии «что если» W1–W10:** открыть больницу, закрыть больницу, школа, колледж, ЖД-платформа, ремонт трассы, автобус, аэропорт, ТЦ или парк, пакет мер.
- **Время доезда скорой помощи** до каждого населённого пункта: дороги OSM с максимальными разрешёнными скоростями, уклон и высота дорог по рельефу SRTM, диапазон погрешности, норматив 20 минут и покрытие районов и субъектов.
- **Чат-помощник на Claude** (Anthropic API) с базой знаний (RAG). Числа он берёт только из расчётных функций, выдуманные числа в ответ не попадают.
- **Мониторинг:** Prometheus, Grafana, Loki, Alloy.

## Как всё устроено

```text
 OpenStreetMap, статистика  ──►  ML-часть (graph, clast, scripts)
                                   │  граф дорог, кластеры Leiden,
                                   │  матрица времени, транспортный индекс (ИТС)
                                   ▼
                          data / graph / clast / ml_results
                                   │ читает (только чтение)
                                   ▼
 Браузер ◄── web (Next.js) ◄──► backend (FastAPI) ──► PostgreSQL + PostGIS + pgvector
                                   │                  Redis (кеш, лимиты)
                                   │                  Claude, Anthropic API (чат)
                                   │                  OSRM (маршруты, пока не подключён)
                                   ▼
                      Prometheus, Loki, Alloy ──► Grafana
```

- **ML-часть** строит дорожный граф, делит его на сообщества и считает транспортный индекс.
- **Бэкенд** индекс не пересчитывает по-своему: он читает файлы ML и подключает модель через контракт (`IndexEngine` и YAML-конфиг).
- **Фронтенд** общается только с API бэкенда.

## Быстрый старт

Что нужно установить:

- Docker Desktop или Docker Engine с Compose v2: для бэкенда и мониторинга;
- Node.js 20.9 или новее: для фронтенда;
- Python 3.12 или новее: только для запуска API без Docker и для тестов.

### 1. Бэкенд

Команды одинаково работают в PowerShell и в bash. Все команды `docker compose` и `python` ниже запускайте из папки `backend`.

Если файл `backend/.env` уже есть, не копируйте его заново: в нём могут быть ваши порты и ключ Anthropic API. Перенесите из `.env.example` только недостающие переменные.

```bash
cd backend
cp .env.example .env              # настройки и порты
docker compose up -d --build      # база, Redis, API и мониторинг
docker compose run --rm api python -m app.cli seed   # справочники, территории, реальные данные OSM, база знаний чата
docker compose run --rm api python -m app.cli load-ambulance   # время доезда скорой до всех населённых пунктов (~20 с)
```

Что делают команды:

- `up` собирает образы и запускает PostgreSQL 16 (с PostGIS и pgvector), Redis, API и мониторинг. При старте API сам применяет миграции базы.
- `seed` загружает справочники, 7 субъектов, 144 района и 3 403 населённых пункта, объекты и признаки из OpenStreetMap (`geo-embeddings/data/osm_poi.csv` и `osm_features.csv`) и базу знаний чата. Синтетические значения, оставшиеся от старых версий, удаляются. Команду можно запускать повторно, дубликатов не будет.
- `load-ambulance` считает время доезда скорой до каждого населённого пункта по дорожному графу ML (`graph/`, Git LFS) и рельефу SRTM, плитки которого лежат в `backend/data/srtm`. Подробности — в разделе «Время доезда скорой помощи» файла [backend/README.md](backend/README.md).

### 2. Фронтенд

Во втором терминале, из корня репозитория:

```bash
cd web
npm install    # зависимости, достаточно один раз
npm run dev    # приложение на http://localhost:3000
```

Фронтенд обращается к API по адресу `http://localhost:8000`. Если API работает на другом адресе, укажите его в `web/.env.local`, например `NEXT_PUBLIC_API_URL=http://localhost:8080`. Бэкенд принимает запросы браузера только с адресов из `CORS_ORIGINS` (по умолчанию `http://localhost:3000`).

## Включить чат

Без ключа работают карта, индекс, сравнение, сценарии и поиск по базе знаний. Чат работает на Claude и требует ключ Anthropic API.

1. Создайте ключ в консоли [platform.claude.com](https://platform.claude.com) (раздел API keys).
2. Добавьте его в `backend/.env`:

   ```text
   ANTHROPIC_API_KEY=<ключ>
   ```

3. При желании смените модель или глубину рассуждений. По умолчанию `LLM_MODEL=claude-sonnet-5-5` и `LLM_EFFORT=medium`; быстрее и дешевле `claude-haiku-5-5`.
4. Пересоздайте контейнер API: `docker compose up -d api`. Команда `docker compose restart` новые переменные из `.env` не подхватывает.
5. Проверьте подключение. Проверка бесплатная, токены не тратятся:

   ```bash
   docker compose run --rm api python -m app.cli chat-check
   ```

Файл `.env` в git не попадает, поэтому ключ передавайте коллегам вне репозитория. Anthropic API доступен не из всех стран: если `chat-check` сообщает об ошибке доступа (403), запрос пришёл из неподдерживаемого региона.

## Данные

Все значения признаков реальные. OpenStreetMap читается один раз скриптами ML, результаты лежат в репозитории в виде CSV, а бэкенд только загружает их командой `seed`. Во время работы сервис к OSM не обращается.

| Шаг | Что делает | Результат |
|---|---|---|
| `scripts/20_fetch_osm_poi.py` | читает выгрузку Geofabrik по СКФО (тот же источник, что у дорожного графа) | `geo-embeddings/data/osm_poi.csv`: 15 372 объекта — больницы, поликлиники и ФАП, школы, детские сады, колледжи и вузы, кафе, ДК, спортивные объекты, парки, ТЦ, рынки, ЖД- и автостанции, аэропорты |
| `scripts/21_calculate_osm_features.py` | считает время на машине по дорожному графу и число объектов в пределах 15 и 30 минут | `geo-embeddings/data/osm_features.csv`: признаки F01–F17 и F21 для 3 403 населённых пунктов |

Данные OSM на 11.11.2026, © участники OpenStreetMap, лицензия ODbL. Чтобы обновить, выполните `python scripts/20_fetch_osm_poi.py --refresh`, затем `python scripts/21_calculate_osm_features.py`, затем `docker compose run --rm api python -m app.cli seed-osm`. Зависимости скриптов перечислены в `scripts/requirements-osm.txt`.

Чего пока нет:

- статистики Росстата, ЕМИСС и ФНС (F18–F20, F22–F30) и климата (F24–F26). Эти признаки не участвуют в расчёте, поэтому субиндекс «Климат» и бейдж привлекательности пустые;
- времени пешком и на общественном транспорте: для профилей без машины используется время на машине;
- полного покрытия OSM в сёлах: малое число объектов иногда значит, что их просто нет на карте. Станций скорой помощи в OSM всего около двадцати, поэтому базой скорой считается и больница.

Отчёт о полноте данных: `python -m app.cli coverage` или `GET /data/coverage`. Если в базе остались синтетические значения от старых версий, это видно везде: `/healthz` пишет `feature_data: synthetic-demo (NOT real data)`, чат предупреждает, в Grafana горит индикатор «Синтетические данные». Команда `seed` (или `clear-demo-features`) их удаляет.

Другие загрузки (все запускаются как `python -m app.cli <команда>`, в Docker через `docker compose run --rm api`):

| Команда | Что делает |
|---|---|
| `seed-osm` | только объекты и признаки OSM из `geo-embeddings/data` |
| `load-features FILE` | признаки F01–F30 от ML (parquet или CSV, длинный или широкий формат) |
| `load-poi` | объекты (больницы, школы и др.) из GeoJSON или таблицы с lon/lat |
| `load-travel-times` | матрица времени до объектов |
| `load-stats FILE --feature F23` | статистика ЕМИСС, Росстата, «Точно», ФНС по районам и субъектам |
| `load-od-matrix FILE` | матрица «Точно» город — город |
| `load-knowledge FILE --source team-data --replace --embed` | свои материалы в базу знаний чата |
| `export-openapi` | обновить `openapi.json` |

Полный список: `python -m app.cli --help`.

## ML-часть: граф, кластеры, индекс

ML-часть отвечает за транспортный граф, кластеризацию дорожной сети и транспортный индекс. Готовые результаты лежат в репозитории, поэтому для запуска продукта граф пересчитывать не нужно.

**Что сделано:**

- Дорожный граф OpenStreetMap: **2 234 894 вершины и 4 625 149 направленных рёбер**. Вес ребра — время проезда по длине, категории дороги, покрытию, направлению движения и ограничениям.
- Аудит графа: 0 некорректных весов и 0 петель. Крупнейшая связная часть сети — 2 187 952 вершины.
- Кластеризация алгоритмом **Leiden**: 1 078 транспортных кластеров, из них 912 содержат населённые пункты. 3 387 пунктов получили кластер, 16 остались вне кластеров.
- Матрица времени поездок между **3 403 населёнными пунктами** (11 576 406 направленных пар) по алгоритму Дейкстры. Пробный расчёт показал 99,53 % достижимости.
- Показатели доступности для населённых пунктов и **144 муниципальных образований**.

**Транспортный индекс (ИТС)** строится из трёх метрик:

| Метрика | Что показывает |
|---|---|
| **Closeness** | как быстро из пункта можно добраться до остальных |
| **Gravity** | доступное население с учётом снижения интереса при росте времени в пути |
| **Betweenness** | транзитная роль узла: как часто через него проходят кратчайшие маршруты |

$$
I_i = 100 \cdot (w_C C_i + w_G G_i + w_B B_i), \quad w_C + w_G + w_B = 1
$$

Здесь $C_i$, $G_i$, $B_i$ — нормированные метрики, $w$ — их веса. Предварительные веса модели 0,4 / 0,4 / 0,2 (доступность, притяжение, транзит) — гипотеза, которую нужно проверить.

> **Статус на сегодня.** В текущем расчёте используются Closeness и Gravity с равными весами. Betweenness предусмотрена моделью, но её включение требует завершения вычислений. Betweenness считается приближённо, по выборке маршрутов.

**Общий индекс** устроен в три слоя: 30 признаков, 7 субиндексов, итог 0–100. Признаки нормируются внутри кластеров похожести (обрезка выбросов и квантили), чтобы большие города не доминировали. Веса обучаются на данных: логистическая регрессия на парных сравнениях территорий (качество меряется коэффициентом Kendall τ) и ранжирующая модель CatBoost YetiRank на миграционном прокси. Признаки F27–F28, повторяющие миграцию, исключены, чтобы модель не «подглядывала» в ответ. Транспортный индекс питает признаки F14–F19 и F21.

**Как ML подключается к бэкенду:**

1. YAML-конфиг модели (путь в `MODEL_CONFIG_PATH`): субиндексы, признаки, веса, кластеры, пресеты. Версия и хеш записываются в таблицу `model_version`.
2. Калькулятор индекса: класс с интерфейсом `app.scoring.contract.IndexEngine`, подключается через `SCORING_ENGINE=пакет.модуль:Класс`. Пока он не подключён, работает встроенный `reference.py`.
3. Признаки: команда `load-features`.
4. Объекты и матрица времени: `load-poi` и `load-travel-times`.
5. OSRM для точных маршрутов: `OSRM_CAR_URL` и `OSRM_FOOT_URL`.

Свойства движка (одинаковый результат при одинаковых данных, сумма вкладов равна итогу, значения в допустимых диапазонах) проверяет `backend/tests/unit/test_engine_contract.py`. Его можно прогнать и против движка ML.

**Валидация.** Сейчас проведена первичная ручная проверка: индекс визуализирован на карте, сопоставлен с положением пунктов и проверен на контрольных территориях и в региональных центрах. Это предварительная проверка, она не заменяет количественную. В планах: сравнение с независимыми показателями, проверка устойчивости рейтингов, анализ чувствительности весов.

## Бэкенд: API, сценарии, чат и RAG

### API

Полный контракт: `http://localhost:8000/docs` и `backend/openapi.json`.

| Назначение | Эндпоинты |
|---|---|
| Территории и карта | `GET /territories`, `GET /territories/geojson`, `GET /territories/{id}` |
| Индекс | `GET /index` (параметры `territory_id`, `cluster`, `sort`, `region`, `group_by`) |
| Объяснение | `GET /explain/{id}` |
| Сравнение | `POST /compare` (2–3 территории одного кластера) |
| Сценарии | `GET /whatif/scenarios`, `POST /whatif/run`, `GET /whatif/runs/{id}` |
| Скорая помощь | `GET /ambulance/settlements/{id}`, `GET /ambulance/settlements`, `GET /ambulance/summary`, `GET /ambulance/method` |

Ошибки всегда приходят в формате `{"code", "message", "details?"}`. Число запросов ограничено по IP через Redis.

### Сценарии what-if

Сценарий — это набор поправок к значениям признаков. Индекс затем считается обычным способом, поэтому территории, которых сценарий не касается, не меняются.

| Код | Что моделирует |
|---|---|
| W1 | открытие больницы или ФАП |
| W2 | закрытие больницы |
| W3 | открытие детского сада или школы |
| W4 | открытие колледжа или филиала вуза |
| W5 | открытие ЖД-платформы |
| W6 | ремонт трассы (время до центра сокращается на заданный процент) |
| W7 | автобус «село — райцентр» |
| W8 | расширение аэропорта |
| W9 | открытие ТЦ, кинотеатра или парка |
| W10 | пакет для района: W1 + W3 + W7 |

Каталог `GET /whatif/scenarios` подсказывает форме параметры каждого сценария и содержит рабочие примеры запросов.

Время до нового объекта берётся из OSRM, если он подключён. Без него оно оценивается аналитически: расстояние по прямой × 1,3 и скорость 50 км/ч на машине или 4,5 км/ч пешком (не меньше 3 минут). В этом случае ответ содержит предупреждение. Если слоя объектов нет, сценарий W2 считает указанную точку закрываемой больницей и оценивает новое время через соседние пункты, а ответ помечается как оценка.

### Чат и RAG

Claude (по умолчанию Sonnet 5.5) использует три инструмента: `get_index`, `compare_territories`, `run_scenario`. Все числа о территориях он берёт только из них. Бэкенд проверяет ответ: каждое число должно встречаться в результатах функций или в найденных фрагментах, неподтверждённые числа пользователю не показываются. Предупреждение о синтетических данных добавляет код, а не подсказка модели.

База знаний хранит справочные фрагменты о методике, признаках, субиндексах, кластерах и профилях. Поиск гибридный: русский полнотекстовый индекс PostgreSQL и косинусный поиск pgvector по локальным эмбеддингам FastEmbed. Результаты двух поисков объединяются по местам в выдаче. Если векторный поиск недоступен, остаётся полнотекстовый.

Проверка поиска без ключа Anthropic API:

1. http://localhost:8000/knowledge/status — поля `chunks` и `embedded` должны быть больше нуля.
2. http://localhost:8000/knowledge/search?q=больница&limit=5 — найденные фрагменты, методы поиска (`vector`, `full_text`) и ссылка на источник.

Контрольные вопросы чата: `python -m app.cli chat-eval --yes` (платно: вызывает Anthropic API).

## Мониторинг

Мониторинг запускается тем же `docker compose up -d`, что и API.

- **Prometheus** каждые 15 секунд собирает метрики с `/metrics` и хранит их 15 дней.
- **Loki** хранит журналы API 7 дней, **Alloy** передаёт в него новые строки.
- **Grafana** (http://localhost:3001) автоматически загружает три панели папки «Атлас СКФО»: «Сервис и скорость», «Качество и происхождение данных», «Сценарии, маршрутизация и журналы».

Четыре правила оповещений (локальные, никуда не рассылаются): `AtlasApiUnavailable`, `AtlasHighServerErrorRate`, `AtlasDataMetricsStale`, `AtlasSyntheticDataPresent`.

Панели пустые, пока нет запросов: графики строятся по окну в 5 минут. Откройте несколько страниц приложения и запустите сценарий what-if.

Журналы API в Grafana (Explore, источник Loki):

```logql
{job="atlas",service="api"} | json
```

Панели создаёт скрипт `backend/observability/build_dashboards.py`: правьте скрипт, а не JSON, затем выполните `python observability/build_dashboards.py` и `docker compose restart grafana`.

## Тесты

Из папки `backend`:

```bash
pytest tests/unit -q    # без базы данных
pytest tests -q         # вместе с интеграционными, нужен TEST_DATABASE_URL
```

Для интеграционных тестов `docker compose` заранее создаёт базу `atlas_test`. Укажите её в `backend/.env`:

```text
TEST_DATABASE_URL=postgresql+asyncpg://atlas:atlas@localhost:5432/atlas_test
```

Интеграционные тесты пересоздают схему, проверяют, что миграция совпадает с моделями, загружают реальные территории ML и прогоняют API, ETL и чат. Вместо Claude чат использует подставной клиент, поэтому сеть не нужна и токены не тратятся. Отдельные модули проверяют загрузку реальных данных OSM и время доезда скорой на реальном дорожном графе и рельефе SRTM. На 13.11.2026 проходят все 145 тестов: 107 unit и 38 интеграционных.

## Если что-то не работает

| Симптом | Что сделать |
|---|---|
| Порт уже занят | Поменяйте нужный `*_PORT` в `backend/.env` и выполните `docker compose up -d` |
| Чат отвечает «Чат не настроен: нет ключа Anthropic API» | Добавьте `ANTHROPIC_API_KEY` в `backend/.env` и выполните `docker compose up -d api` |
| Ошибка ключа или доступа (401, 403) в чате | `docker compose run --rm api python -m app.cli chat-check` покажет причину |
| `/healthz` показывает `feature_data: empty` | Признаки не загружены: выполните `seed` (или `seed-osm`) |
| Панели Grafana пустые | Откройте несколько страниц приложения и подождите |
| Интеграционные тесты пропускаются | Не задан `TEST_DATABASE_URL` |
| Фронтенд не видит API | Проверьте `NEXT_PUBLIC_API_URL` в `web/.env.local` и `CORS_ORIGINS` в `backend/.env` |

## Статус и ограничения

Состояние на 13.11.2026: прототип работает на реальных данных OpenStreetMap, все 145 тестов проходят, чат работает на Claude Sonnet 5.5, мониторинг развёрнут.

- **12 из 30 признаков без данных** (F18–F20, F22–F30: статистика и климат, которых нет в OSM). Они не участвуют в расчёте.
- **OSRM не подключён.** Время в сценариях W1–W5 и W9 оценивается по прямой с поправкой 1,3. Сценарий W2 без слоя объектов — оценка.
- **Betweenness не включён** в текущий расчёт транспортного индекса, веса ИТС пока гипотеза.
- **Валидация предварительная:** ручная проверка на карте без количественных метрик.
- Индекс не учитывает сезонность, пробки, стоимость проезда, расписания транспорта, качество услуг и цены на жильё.
- Модель зависит от полноты OpenStreetMap и данных о населении. Маршруты могут выходить за границы СКФО, а в графе этих дорог нет.
- Веса пресета «Риелтор / инвестор» в сумме дают 90, а не 100. При загрузке они приводятся к 100 с предупреждением в журнале.
- Райцентры определяются эвристикой (крупнейший пункт района), ошибки правятся в `backend/seeds/cluster_overrides.csv`.
- У районов из данных ML нет ОКТМО, он заполняется при загрузке статистики с `--learn-oktmo`.
- Индекс считается для населённых пунктов. Значения районов и субъектов — агрегаты.

## Планы развития

1. Загрузить реальные признаки и подключить OSRM (авто и пешком).
2. Завершить расчёт Betweenness и проверить веса ИТС анализом чувствительности.
3. Количественная валидация: сравнение с независимыми показателями, устойчивость рейтингов, оценка качества RAG на 50–100 вопросах.
4. Дополнить данные о населении (Росстат, ФИАС) и ОКТМО районов.
5. Пилот в одном муниципалитете СКФО (3–5 реальных сценариев), сравнение с миграцией Росстата и опросом жителей.
6. Feature propagation: графовое восстановление недостающих признаков.
7. Масштабирование на другие федеральные округа (объединение региональных графов, буферные зоны).
